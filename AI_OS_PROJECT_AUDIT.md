# AI OS Project Audit

## Назначение

Этот проект выглядит как ранняя основа для локальной "операционной системы ИИ":

- ядро памяти и поиска
- агентный цикл с менеджерами и воркерами
- локальный API
- операторская панель
- pipeline для загрузки и анализа накопленных чатов

Сейчас в папке уже есть полезный фундамент, но он смешан с временными ремонтными скриптами, дубликатами, архивами и частично сломанными файлами.

## Краткий вывод

Проект не нужно выбрасывать. Его нужно собрать вокруг одного основного пути запуска и разделить на 4 слоя:

1. `kernel`
2. `memory`
3. `agent runtime`
4. `control plane`

В текущем состоянии лучшая база для восстановления находится в папках `core`, `scripts`, `memory`, `dashboard`.

## Что оставить как основу

### 1. Память и поиск

Сохранять как фундамент:

- `core/memory_engine.py`
- `core/retrieval_engine.py`
- `core/graph_engine.py`
- `core/temporal_engine.py`
- `scripts/runtime_store.py`
- `GPTMemory_runtime.yaml`

Почему:

- это самая связная часть проекта
- она уже умеет хранить записи, нормализовать их, искать, строить связи и отдавать recent view
- это естественная база для AI OS memory subsystem

### 2. Локальный API для control plane

Сохранять как временный основной API:

- `scripts/api_server.py`
- `dashboard/index.html`

Почему:

- это самый прямой и понятный путь запуска
- API уже связывает память, поиск, граф и snapshot
- статическая панель проще React-ветки и ближе к режиму "операторской консоли"

### 3. Данные и knowledge pipeline

Сохранять как отдельный data layer:

- `memory/chat_loader.py`
- `memory/chat_parser.py`
- `memory/knowledge_builder.py`
- `memory/vector_memory.py`
- `memory/chats`
- `memory/parsed`
- `memory/knowledge`
- `memory/embeddings`

Почему:

- это уже похоже на ingestion pipeline для долговременной памяти
- из этого можно сделать отдельный memory ingestion service

## Что заморозить как legacy

Эти части не удалять сразу, но перестать считать их основным runtime:

- `scripts/api_gui_integration.py`
- `core/cognitive_loop_api.py`
- `core/cognitive_loop_api_v2.py`
- `GPTMemoryEngine/`
- корневые скрипты вида `fix_*`, `upgrade_*`, `dashboard_*`, `add_*`, `rebuild_*`, `restore_*`
- `.bak` файлы

Почему:

- это параллельные ветки идеи, а не единый продуктовый поток
- они увеличивают шум и мешают понять, что действительно является системой
- часть из них поломана или содержит плейсхолдеры

## Что считать архивом, а не кодом продукта

Следующие папки лучше воспринимать как данные или технические остатки:

- `backup_python_files`
- `backups`
- `stable_backup`
- `smart_trash`
- `logs`
- `.gptcollector`

Их не стоит смешивать с runtime-кодом AI OS.

## Критические проблемы

### 1. Массово сломан Python-синтаксис

Около 40 Python-файлов имеют поврежденные заголовки вида `\"""` в начале файла.

Это критично, потому что:

- часть модулей не импортируется
- `compileall` падает
- агентная и когнитивная подсистемы фактически ненадежны

### 2. Секреты в коде

В `scripts/api_gui_integration.py` захардкожены Telegram token и chat id.

Это критично, потому что:

- секреты нельзя безопасно хранить в кодовой базе
- любая публикация или резервная копия превращается в утечку

### 3. Несогласованность интерфейсов

React dashboard и статический dashboard живут параллельно.

Сейчас:

- `apps/dashboard` ходит в `127.0.0.1:5000`
- `scripts/api_server.py` работает на `127.0.0.1:8010`
- React-ветка не в воспроизводимом состоянии

### 4. Несогласованность классов и API

Есть прямые несовпадения контрактов:

- `cognitive_loop.py` вызывает `manager.run_task(...)`, но `ManagerBase` содержит `perform_task(...)`
- `scripts/full_db_integration.py` создает `RetrievalEngine()`, `GraphMemory()`, `TemporalMemory()` без обязательных аргументов

Это означает, что часть "AI OS" логики сейчас номинальная, а не реально исполняемая.

### 5. Смешение конфигурации и данных

`GPTMemory_runtime.yaml` по факту хранится как JSON.

Это не ломает проект сразу, но:

- путает инструменты и ожидания
- мешает нормальной эволюции конфигурации

## Как переназначить текущие папки

### Оставить и развивать

- `core` -> будущий `memory` и часть `kernel`
- `agents` -> будущий `agents`
- `scripts/api_server.py` -> база для будущего `api/app.py`
- `dashboard` -> временная операторская панель
- `memory` -> будущий `data` и `memory/ingestion`

### Вынести позже

- `GPTMemoryEngine` -> либо удалить после сверки, либо перенести в `legacy/GPTMemoryEngine`
- `apps/dashboard` -> либо починить и сделать основным UI, либо перенести в `legacy/web-dashboard`
- корневые ремонтные скрипты -> `legacy/repair-scripts`

## Что удалить сразу не стоит

Не рекомендую сразу удалять:

- `memory/chats`
- `storage`
- `GPTMemory_runtime.yaml`
- `GPTMemoryEngine`

Причина:

- это либо пользовательские данные, либо исторический код, который еще может понадобиться для сравнения и миграции

## Что лучше считать MVP для AI OS

Реалистичный MVP этого проекта:

- локальная память с добавлением, поиском, тегами и временной шкалой
- граф связей между записями
- очередь задач
- регистр агентов
- API управления
- локальная панель оператора
- ingestion чатов в долговременную память

Это уже похоже на "AI OS control core", даже без полноценной автономии.

## Приоритет восстановления

### Этап 1. Стабилизация кода

- исправить сломанные Python-заголовки
- убрать секреты из кода
- выбрать один основной API
- выбрать один основной dashboard

### Этап 2. Сведение архитектуры

- перестроить дерево проекта вокруг `api`, `memory`, `agents`, `kernel`
- убрать дублирующие entrypoint-файлы
- отделить runtime-код от архивов и генераторов

### Этап 3. Настоящая агентная система

- ввести нормальный `Agent` protocol/interface
- сделать планировщик задач
- сделать registry агентов
- ввести события, статусы, heartbeats, результаты выполнения

### Этап 4. Долговременная память AI OS

- объединить runtime memory и chat ingestion
- ввести snapshot policy
- добавить semantic retrieval поверх vector memory

## Первая практическая цель

Если проект развивать именно как AI OS, то ближайшая правильная цель не "добавить еще один скрипт", а:

"Собрать единый локальный AI OS runtime, который поднимает память, API, очередь задач и операторскую панель из одного entrypoint."

## Рекомендуемый следующий шаг

Следующее практическое действие:

1. Починить синтаксически поврежденные Python-файлы.
2. Зафиксировать один основной runtime.
3. Вынести legacy-ветки в отдельную папку.
4. Собрать единый `main.py` или `api/app.py` как точку запуска AI OS.

## Решение по текущему проекту

Вердикт:

- проект жизнеспособен
- у него есть полезное ядро для AI OS
- главная проблема не в отсутствии идеи, а в распаде структуры и накоплении временных решений

То есть это не "мусорная папка", а "сырой AI OS prototype", который нужно аккуратно собрать в систему.
