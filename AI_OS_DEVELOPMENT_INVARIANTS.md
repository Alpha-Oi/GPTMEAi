# AI OS Development Invariants

Этот документ фиксирует, какую исходную логику проекта GPTMEAi / AI OS мы сохраняем во время дальнейшей переработки.

## Главный принцип

Мы не меняем замысел проекта. Мы приводим его в рабочую инженерную форму.

То есть цель не "сделать другой проект", а:

- сохранить исходную идею AI OS
- убрать хаос структуры
- собрать единый runtime
- повысить надежность

## Неприкосновенные инварианты

### 1. Проект остается AI OS, а не просто чат-приложением

Система должна развиваться как локальная операционная среда для ИИ, а не как обычный чат-интерфейс.

Это означает:

- наличие состояния системы
- наличие памяти
- наличие задач
- наличие агентов
- наличие control plane

### 2. Память остается ядром системы

Подсистема памяти не является второстепенной фичей.

Она должна сохранять центральную роль:

- долговременное хранение записей
- поиск
- временная шкала
- граф связей
- дальнейшая semantic retrieval логика

### 3. Ingestion исторических чатов сохраняется

Корпус чатов, парсинг, knowledge graph и embeddings не считаются мусором.

Это часть будущей долговременной памяти AI OS.

Можно менять:

- структуру модулей
- точки запуска
- API вокруг ingestion

Нельзя менять сам принцип:

- AI OS должна уметь использовать накопленную историю как knowledge base

### 4. Агентная модель сохраняется

Проект сохраняет идею агентной координации.

Даже если реализация будет меняться, базовые сущности сохраняются:

- manager
- worker
- task
- queue
- runtime state

Можно переписать механизм выполнения, но нельзя выбросить саму идею агентного слоя без отдельного решения.

### 5. Control plane должен оставаться явным

Системой должно быть возможно управлять и наблюдать за ней извне.

Это означает сохранение:

- локального API
- операторской панели
- health/status слоев
- inspectable состояния runtime

AI OS не должна превращаться в "черный ящик".

### 6. Локальный first-подход сохраняется

Основной сценарий проекта остается локальным.

То есть:

- локальный запуск важнее облачной зависимости
- локальные данные важнее внешних сервисов
- локальный dashboard и API считаются базовыми

Внешние интеграции допустимы, но не должны становиться обязательным условием существования системы.

### 7. Пользовательские данные не должны ломаться от рефакторинга

Рефакторинг не должен уничтожать или произвольно перезаписывать:

- `GPTMemory_runtime.yaml`
- `storage/`
- `memory/chats/`
- `memory/parsed/`
- `memory/knowledge/`
- `memory/embeddings/`

Если потребуется миграция форматов, она должна быть:

- явной
- обратимой или безопасной
- документированной

### 8. Официальный runtime должен быть один

У проекта может быть много исторических веток, но официальный runtime должен быть один.

Это нужно для:

- предсказуемого запуска
- отладки
- развития архитектуры

Legacy-ветки допустимы, но они не должны снова конкурировать с основным путём запуска.

### 9. Refactor допускается, подмена смысла нет

Разрешено:

- переносить код по новым пакетам
- унифицировать config
- добавлять manifest
- стабилизировать API
- добавлять compatibility layers
- убирать дубли
- отделять legacy

Нельзя без отдельного решения:

- отменять AI OS логику
- выкидывать память как ядро
- убирать агентный runtime как класс подсистемы
- превращать проект только в dashboard
- превращать проект только в corpus parser

### 10. Архитектура должна идти к 4 главным слоям

Будущая структура должна постепенно сходиться к этим слоям:

- kernel
- memory
- agent runtime
- control plane

Это стратегическое направление проекта.

### 11. У проекта должен быть developer-context

В проекте должна существовать отдельная developer-документация, из которой новый разработчик может быстро понять:

- что это за система
- зачем она создаётся
- какова её архитектура
- какая структура файлов считается основной
- что за что отвечает
- на какой стадии находится разработка

После каждого серьёзного изменения эта документация должна обновляться.

### 12. Временная разработческая деятельность не должна засорять корень проекта

Для временных скриптов, логов, промежуточных заметок, отчётов и change notes должна использоваться отдельная папка разработки.

Новые временные материалы не должны по умолчанию складываться в корень проекта, если они не являются частью официального runtime, data layer или постоянной архитектурной документации.

## Что можно менять свободно

Следующие изменения не считаются нарушением замысла:

- переименование внутренних модулей
- перенос кода из `scripts/` в `ai_os/`
- замена дублирующих entrypoint-файлов
- добавление новых API endpoints
- улучшение dashboard
- стабилизация форматов и конфигурации
- добавление runtime manifest
- добавление новых agent lifecycle методов

## Что требует отдельного подтверждения

Следующие изменения уже считаются концептуальными и требуют отдельного решения:

- отказ от агентной модели
- отказ от долговременной памяти
- удаление historical corpus
- переход на обязательную облачную архитектуру
- полный отказ от локального control plane
- замена AI OS идеи на просто knowledge dashboard
- отказ от developer-context и истории серьёзных изменений

## Практическое правило на будущее

Каждый следующий большой рефактор должен отвечать на 2 вопроса:

1. Это делает AI OS более цельной системой?
2. Это сохраняет исходную роль памяти, агентов и control plane?

Если ответ "нет", значит это уже не просто техническая переработка, а смена направления.
